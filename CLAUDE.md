## 1. What this project is

**Samsung PRISM GenAI Hackathon 3rd Edition (Y2026–27), Theme 02 — Smart Guided Troubleshooting Engine.**

A REST API that converts a vague Galaxy device complaint into a grounded, ordered,
schema-valid troubleshooting plan with verified in-app Settings deeplinks.

**Deadline: 25 September 2026, 23:59 IST.** Submission is a GitHub repo tagged
`PRISM_GENAI_HACKATHON_Y2026`, a ≤5-minute demo video, and a PPT. Judging weights:
working prototype 30%, technical depth 25%, innovation 20%, theme relevance 15%,
presentation 10%.

**This project is scope-locked.** Do not propose, scaffold, or build anything that is not
traceable to Samsung's Theme 02 materials or to §5 below. If an idea is interesting but
not in scope, say so in one line and move on.

## 3. Frozen decisions — never change these without being asked

1. **`data/schema.py` is immutable.** SHA-256 `649440e0309b25dc5363039fc28dd7f21b71177779b909def8757b41e76ebf6b`.
   `backend/app/schema_samsung.py` is a byte-identical copy. Both are asserted in CI.
   If output does not fit the schema, **fix the output, never the schema.**
2. **`siis_response` is supplied with the request, not retrieved by us** (C1–C4).
   Do not build a document search engine over the articles.
3. **`deeplinks.json` (578 entries) is the retrieval corpus.** The masked URI is never
   indexed and never matched on (C6, guide §7.4). Match only on `message`,
   `description`, `qna_description`.
4. **The LLM is a parser, not an authority.** One call, on the extraction stage only. It
   receives the article and returns structure plus source spans. `ir.py` deliberately has
   **no deeplink field** — the model cannot name a URI even if it tries. Keep it that way.
5. **Resolver gate order is fixed:**
   `[0] short-circuit → [1] retrieval → [2] polarity → [3] scope → [4] target-concept →
   [5] margin → [6] catalog identity`
6. **Three legal resolution outcomes, no fourth:** exact catalog entry,
   `bixby://dummy_positive`, `null`.
7. **Five internal ordering tiers**, emitted category stays `auto|manual|critical` only.
   `critical` is always last.
8. **Envelope is `{query, query_variations, response, meta}`.** Only `response` is
   validated against `ContextDeeplinkResponse`. Never nest telemetry inside it.
9. **`score` comes from the formula in contract §3.4.** The model never picks it.
10. **Endpoints:** `POST /v1/troubleshoot` and `GET /health` are Samsung's. `GET /metrics`
    is ours and is labelled non-spec.

## 4. Hard rules

**Never:**
- Edit `data/` or `schema_samsung.py`.
- Hardcode any fixture text, complaint string, article sentence, or catalog URI into
  `backend/app/**`. `bixby://dummy_positive` is the single allowed exception (the spec
  names it). A CI test enforces this — do not weaken that test to make code pass.
- Write a performance number by hand. Every figure in `docs/metrics.md` is generated by
  `python -m evaluation.run_eval`. If you cannot measure it, say so and leave it out.
- Emit a URL (`http`, `https`, `www.`, markdown link) anywhere in a response.
- Let a `manual` action carry a deeplink, or a device operation (restart / safe mode /
  recovery) carry one.
- Add FAISS, Redis, a cross-encoder, LangChain, multi-agent orchestration, a database, or
  any new framework. All were explicitly rejected — see Phase 0 §7.
- Relax or delete a failing test to get green. Fix the code, or explain why the test is
  wrong and wait.

**Always:**
- Run `python -m pytest` before saying anything is done. It must be **fully green**.
- Put tunables in `backend/app/config.py`, lexicons in `data/lexicons/`, never inline.
- Add a regression test for every bug you fix, with a docstring stating what was observed.
- Assert the *contract*, not the *mechanism*. A test that pins which gate catches something
  will break on improvements. (This already happened twice — see
  `test_factory_reset_trap_is_never_emitted`.)
- Keep the offline path working. `LLM_PROVIDER=stub` must never need a key.

**Measured** (`python -m evaluation.run_eval --provider gemini --rate-limit-rpm 12`,

| Gate ablation, V0 → V4 | wrong 31.6% → 1.2%, precision 68.4% → 98.7% |
| Schema-valid / rule-compliant, 20 rows | 100% / 100% |

| Latency p50 / p95 (live provider) | 3217 ms / 4727 ms |
| Cost, 20 rows | $0.034 |

Notes on the numbers, so they are not over-read:
- The gold set is **derived from the catalog**, not human-labelled. Gold is an
  equivalence class, because 54 `(message, originalType)` classes hold more than one
  entry — `View Notification Settings` alone covers 21 different screens.
- The ablation **cannot measure gate [3] (scope)**: V1 and V2 are identical, because
  every generated step carries its own entry's qualifier by construction. The gate's
  value is shown by the production regression test, not by the ablation.
- `MARGIN_DELTA` stays at **0.08**: a seeded fit half preferred 0.06, but on the held-out
  half that is worth 2 more correct answers and 2 more wrong ones — inside the declared
  5-case materiality bar, and 0.08 has the lower wrong rate.

**Known open bug, not yet fixed:** `parse_intent` scans the whole step for polarity, so a
setting whose own NAME contains "turn on"/"turn off" hijacks the read. "Tap the switch
next to Double tap to turn off screen **to enable it**." parses as OFF and resolves to the
disable entry. 8 catalog entries have such subjects; this accounts for 4 of the 10 wrong
resolutions in the current report. Fix belongs with the resolver, measured by re-running
the harness.

## 6. Commands

```bash
python -m pytest                  # 87 tests, no API key needed
python -m evaluation.run_eval     # regenerate report.json + metrics.md (offline stub)
python -m evaluation.run_eval --provider gemini --rate-limit-rpm 12   # live numbers
python -m tools.demo_row21        # row_21 plan + resolver accept/reject trace
python -m uvicorn app.main:app --app-dir backend --port 8000
```

`backend/` is the import root, not the repo root. Gemini's free tier allows 15
`generate_content` calls per minute; a 20-row live run needs `--rate-limit-rpm 12` to stay
under it.

## 7. How to work

Work in small, verifiable steps. After each: run the tests, state what changed and what it
measured. Do not produce large refactors or multi-file rewrites unprompted.

Before implementing anything non-trivial, state in two or three sentences what you are
about to do and which contract section or task above it serves. If it serves none, stop
and ask.

When you find a bug, say plainly what was observed, what caused it, and what the fix
changes — including anything it makes worse. Do not present a partial fix as complete.

Be direct about uncertainty. "I cannot measure this here" is a better answer than a
plausible number. The project's credibility with the jury rests on every reported figure
being real.
